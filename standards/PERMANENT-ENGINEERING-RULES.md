# LeeWay Permanent Engineering Rules

Authority: LeeWay Standards. Active mission: Golden Package C3. Existing law remains authoritative.

## R01–R12
R01 Recover the last clean Master Checkpoint before continuing work.
R02 Preserve approved decisions unless new evidence invalidates them.
R03 Identify the original objective and active acceptance gate first.
R04 Inspect existing implementations before building alternatives.
R05 Classify ALREADY BUILT, PARTIALLY BUILT, MISSING GLUE, TRULY MISSING.
R06 Establish canonical source, version, runtime owner and hashes before mutation.
R07 Execute verified LeeWay Formula where required.
R08 Reuse Runtime Fabric, Skill Orchestrator, Veritas and canonical authority; no competing brain or control plane.
R09 Diagnose the exact dependency and repair the smallest canonical component.
R10 Treat drive paths as local installation observations, never system identity.
R11 Preserve existing source and user changes; test rollback.
R12 Never bypass authorization, integrity, security or Veritas.

## R13–R24
R13 Process health, skill descriptors, and generated results do not prove execution.
R14 Test real inputs, observable outputs, expected results, and negative cases.
R15 Failed repairs return to the same unfinished mission gate.
R16 Preserve independent functioning providers during a repair.
R17 Do not close a task before its specific acceptance test passes.
R18 Write receipts only for executed actions and learn only from eligible evidence.
R19 Maintain checkpoints across interruptions, errors and conversations.
R20 Finish the approved milestone before broadening scope.
R21 Turn stable repeated work into reusable deterministic capabilities.
R22 Require measurable gains in portability, reliability, reuse or execution.
R23 Apply file standards to LeeWay-authored governed source, not vendor/generated files.
R24 Human approval governs consequential actions and permission changes.
R25 GitHub-First Source and Reuse Authority: At the beginning of every substantive LeeWay engineering task, recover the Master Checkpoint and inspect canonical GitHub repositories, branches, implementations, acceptance contracts, source versions, hashes, and verified evidence. Classify ALREADY BUILT, PARTIALLY BUILT, MISSING GLUE, or TRULY MISSING; extend the canonical owner rather than duplicating it. After implementation, return to GitHub to reconcile commit, PR, CI, provenance, and acceptance status. GitHub owns versioned source and release identity; physical runtime tests separately establish deployed behavior. Never use a particular drive, machine, provider, or historical deployment as canonical identity.

## Required lifecycle
Investigate → Diagnose → Plan → Implement → Test → Validate → Repair → Retest → Verify → Evidence.

If a defect interrupts a task: retain the last checkpoint and objective; identify defect, owner, scope and dependency; verify authority and rollback; repair canonical owner; retest the failure, siblings and regressions; return to original gate; close only with actual Veritas evidence and eligible receipts.

## Prohibitions
Never invent Formula results, hashes, Veritas PASS, receipts, execution history, or physical recovery. Never substitute description for an actual action, discard uncommitted work, kill processes on appearance alone, set hard-coded new drive defaults, replace working components instead of missing glue, or alter packages/data without authorization. Do not announce SK while C3 is open. Security or integrity failures block only affected actions until legitimate repair.
